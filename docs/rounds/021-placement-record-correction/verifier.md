**Findings**

1. **[SHOULD FIX]** `docs/architecture/deck-placement.md:349-360` (§5.1, "Unknown codes" and "Mapped codes") — the description of `GetDummyOrMappedCardData` has the precedence backwards, and one detail is wrong. The text says it "returns the card an id-mapping file maps the code to, if any; otherwise, while `load_dummies` is true, a placeholder with `code = 0` and every other field zero." The source (`gframe/deck_manager.cpp:17-28`) is: `if(!load_dummies) return gDataManager->GetMappedCardData(code);` first, then, only while dummies are on, a lookup or creation of a placeholder with `code = 0` **and `alias = code`**. So while dummy loading is on the id-mapping file is never consulted; a mapped code resolves through the mapping only after dummy loading stops. The line "Mapped codes are classified by the card they map to" (`:360`) is therefore true only in that later phase, and "with placeholders off, `cd` is null and the code is dropped silently" (`:358-359`) ignores a mapped code that resolves in that phase. Failure: someone modelling upstream's unknown-code handling from §5.1 would predict a mapped code is classified by its target during startup, when upstream keeps or drops a code-0 placeholder. No behaviour depends on it today (`classify_card()` asks only its own database, and the new header comment says so). This is inherited from round 020 and in the area the brief asks to make "exhaustive and true" (Goal, part 5).
